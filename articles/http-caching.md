# HTTP 缓存：强缓存与协商缓存的完整链路

缓存是性能优化里性价比最高的一环。理解浏览器的缓存决策流程，能帮你排掉大量「为什么没更新 / 为什么没缓存」的问题。

## 两层缓存

浏览器发起请求时，缓存决策分两层：

1. **强缓存**：命中就直接用本地副本，**不发请求**。
2. **协商缓存**：强缓存失效后，带条件请求去问服务器「变了没」。

## 强缓存：Cache-Control

```
Cache-Control: max-age=31536000, immutable
```

- `max-age`：资源新鲜的秒数。
- `immutable`：告诉浏览器这段时间内别来问，连协商都省了。
- `no-cache`：可以缓存，但每次都要协商。
- `no-store`：完全不缓存。

> 带哈希指纹的静态资源（如 `app.3f2a.js`）最适合 `max-age` 拉满 + `immutable`。

## 协商缓存：ETag 与 Last-Modified

强缓存过期后，浏览器带上标识去问：

```
If-None-Match: "abc123"          # 对应 ETag
If-Modified-Since: Wed, 24 ...   # 对应 Last-Modified
```

服务器判断没变，就回 `304 Not Modified`，**不带 body**，浏览器继续用本地副本。

- **ETag** 更精确（内容哈希），但计算有成本。
- **Last-Modified** 更轻，但秒级精度，且「内容没变但时间变了」会误判。

## 完整决策流程

1. 有本地副本？没有 → 直接请求。
2. 强缓存有效？是 → 用本地副本（from disk/memory cache）。
3. 否则带条件请求 → 服务器 `304` 就复用，`200` 就更新。

## 实践建议

- HTML 用 `no-cache`（保证每次校验），静态资源用长 `max-age` + 文件指纹。
- 别用 `no-store` 一刀切，那等于关掉缓存。

理清这条链路，缓存相关的诡异问题基本都能自己定位了。
